# 伪代码编译器词法分析方案对比研究报告

> 主题：面向初学者的 CIE 9618 伪代码编译器，应当采用**手写（hand-crafted）**还是**正则/工具生成（RE / tool-generated）**的词法分析器？
>
> 方法：从 GitHub fork 三个开源伪代码解释器/编译器，与本项目实现一起，针对同一批反例进行实测对比。

---

## 摘要

本报告对四个 CIE/IGCSE 伪代码实现的词法分析（tokenizer/lexer）方案进行对照实测。我们构造了三组、共 **15 个测试样例**，覆盖「词法健壮性」「正则词法歧义」「Python/CIE 语法混用」三个层面，并以 Cambridge 官方《9618 Pseudocode Guide for Teachers (2026)》作为语法权威依据。

核心结论：

1. **纯正则方案（master-regex）能力上限最低**：对非法字符要么直接崩溃且无位置信息，要么把错误**静默吞掉**——后者在教学场景中是最危险的失败模式。
2. **工具生成方案（Lark）居中**：能给出行列定位，上下文相关词法分析（contextual lexer）甚至能化解部分歧义；但错误信息是「实现者视角」，且语法实现不全会导致**报错位置错位**，缺乏自愈能力。
3. **手写方案上限最高**：可以做到「精准定位 + 领域引导 + 错误分级 + 自动纠正 + 一次多报」五位一体。独立开源项目 beancode 同样选择手写并加入大量领域引导，反向印证了本项目的设计取向。

---

## 1. 研究背景与目标

- **项目定位**：将 CIE 9618 伪代码翻译为可执行 Python 的教学编译器，目标用户是刚接触编程的学生。
- **核心设计目标**：错误信息必须对初学者友好——不只是「报错」，而是要「指出错在哪、为什么错、应该怎么改」，并尽量让程序能继续分析以暴露更多问题。
- **研究问题**：在上述目标下，词法分析应选择手写还是正则/工具生成？
- **研究方法**：fork 三个真实开源项目，与本项目同台实测，用数据而非直觉得出结论。

## 3. 权威语法依据（CIE 9618 官方）

依据 Cambridge International《AS & A Level Computer Science 9618 — Pseudocode Guide for Teachers, for exams in 2026》：

| 语法概念 | CIE 9618 官方写法 | 出处 | 学生常见的 Python/其他语言写法（错误） |
|----------|------------------|------|----------------------------------|
| 注释 | `//` | §1.5「Comments are preceded by two forward slashes //」 | `#`（Python） |
| 赋值 | `←` 或 `<-` | §2.6「The assignment operator is ←」 | `=`（Python/C），`:=`（Pascal） |
| 相等比较 | `=` | 运算符索引 p.17 | `==`（Python/C/Java） |
| 不等比较 | `<>` | 运算符索引 p.17 | `!=`（Python/C/Java） |
| 选择结构 | `IF ... THEN ... [ELSE] ... ENDIF` | §6.1 | — |

> 说明：官方 §6.1 明确规定了 `IF ... THEN ... ENDIF`（ELSE 可选，不支持 ELSE IF，须嵌套）。因此「带 IF 的真实伪代码」是合法且必须支持的结构，第三组测试即据此设计。

## 4. 测试样例与实测结果

> 测试环境：Python 3.13.9 / lark 1.3.1（Windows）。全部样例与脚本见附录，可一键复现。

### 4.1 第一组：词法健壮性

考察「非 ASCII 标点、未闭合字符串、运算符 token 粒度」三类基本鲁棒性。

#### 样例 U1 / A1：全角中文冒号 `：`

输入：`DECLARE x ： INTEGER`

| 实现 | 实测输出 |
|------|----------|
| **USER** | `[Error] L1:C11 - Detected Chinese colon '：'.` + `Hint: Use ':'` + 源码行 + `^` 指针；**自愈**为 `COLON ':'` 继续 |
| **HUI** | `RuntimeError: Unexpected token: ：`（**崩溃**，无行列） |
| **LARK** | `UnexpectedCharacters: No terminal matches '：' ... at line 1 col 11`（有行列，无引导） |

#### 样例 U2 / A2：未闭合字符串

输入：`OUTPUT "hello`

| 实现 | 实测输出 |
|------|----------|
| **USER** | `[Error] L1:C8 - Unterminated string literal.` + `Hint: Add a closing '"'` + 指针定位到引号 |
| **HUI** | `RuntimeError: Unexpected token: "`（**崩溃**且**误导**：仿佛是引号本身非法，而非「未闭合」） |

#### 样例 U3 / A3：运算符 token 粒度

输入：`flag <- 3 + 4 > 5`

| 实现 | token 流（节选） |
|------|------------------|
| **USER** | `PLUS '+'`、`GREATER_THAN '>'`（**细粒度**，parser 拿来即用） |
| **HUI** | `OPERATOR '+'`、`OPERATOR '>'`（**粗粒度**，`+` 与 `>` 同类，parser 须二次判断 value） |

### 4.2 第二组：正则词法歧义探测（针对 LARK）

LARK 的数字终结符定义为 `INT_LITERAL: /-?\d+/`，带可选负号前缀，理论上存在「`5-3` 被吞成 `5` 与 `-3`」的词法歧义。实测：

| 样例 | 输入 | 实测结果 |
|------|------|----------|
| B1 | `x <- 5-3` | **PARSED OK** → `sub(5, 3)` |
| B2 | `x <- 5 - 3` | PARSED OK → `sub(5, 3)` |
| B3 | `x <- a-3` | PARSED OK → `sub(a, 3)` |
| B4 | `x <- 1-1` | PARSED OK → `sub(1, 1)` |
| B5 | `DECLARE x ： INTEGER` | `UnexpectedCharacters: No terminal matches '：' ... col 11` |
| B6 | `x <- 'ab'` | `UnexpectedCharacters: No terminal matches ''' ... col 6`（多字符 CHAR 不合法） |
| B7 | `x <- ''` | `UnexpectedCharacters: No terminal matches ''' ... col 6`（空 CHAR 不合法） |

> **诚实结论**：B1–B4 表明那个理论上的负号歧义**并未发生**。原因是 Lark 的 LALR **上下文相关词法分析器**在读完 `5` 之后，分析器状态期待的是中缀运算符，于是优先把 `-` 识别为减号而非负号前缀。这一点是工具生成方案的**优势**，纯 master-regex 反而做不到。B6/B7 则暴露了 `CHAR_LITERAL: /'[^\\\n]'/` 的刚性：错误信息只说「没有终结符匹配单引号」，并不会告诉学生「CHAR 只能放单个字符」。

### 4.3 第三组：Python/CIE 语法混用（基于官方语法，含 IF）

这是最贴近真实教学场景的一组：学生把 Python 习惯带入伪代码。全部样例均为合法的 CIE 结构，仅在单点混入 Python 写法。

#### 逐项结果

| 用例 | 混用点 | USER | HUI | LARK |
|------|--------|------|-----|------|
| **C1** | `#` 注释 | `[Error] '#' is not a comment symbol` + `Hint: Use '//'`；自愈跳过 | **崩溃** `Unexpected token: #` | `No terminal matches '#' col 1` |
| **C2** | `=` 赋值 | `[Error] Cannot use '=' for assignment` + `Hint: Use '<-'` | **静默放过** `OPERATOR:=` ❗ | `Unexpected token EQUAL col 7` |
| **C3** | `==` 比较（IF 内） | `[Warning] '==' is not valid` + `Hint: Use '='`；自愈成 `=` | **静默放过**，切成两个 `OPERATOR:=` ❗ | 报错位置错位到 `Count` |
| **C4** | `!=` 不等（IF 内） | `[Error] '!=' is not valid` + `Hint: Use '<>'`；自愈成 `<>` | **崩溃** `Unexpected token: !` | 报错位置错位到 `Count` |
| **C5** | 四错混合（IF/ELSE 程序） | **一次报全 4 个**，各带定位+引导+指针 | `#` 处即崩，**后 3 错全部丢失** | `#` 处即停，后续不可见 |

#### C5 综合样例（USER 实测完整输出）

输入程序：

```text
# count check
DECLARE N : INTEGER
N = 5
IF N == 5 THEN
    OUTPUT "five"
ELSE
    OUTPUT "other"
ENDIF
IF N != 0 THEN
    OUTPUT "nonzero"
ENDIF
```

USER 一次性给出全部四条诊断：

```text
diagnostics: 4   |   AST: REJECTED (has error)
[Error]   L1:C1 - '#' is not a comment symbol in pseudocode.
  Hint: Use '//' to start a comment.
  | # count check
  | ^
[Warning] L4:C6 - '==' is not valid in pseudocode.
  Hint: Use '=' for comparison.
  | IF N == 5 THEN
  |      ^
[Error]   L9:C6 - '!=' is not valid in pseudocode.
  Hint: Use '<>' for not-equals comparison.
  | IF N != 0 THEN
  |      ^
[Error]   L3:C3 - Cannot use '=' for assignment.
  Hint: Use '<-' for assignment. '=' is only for comparison.
  | N = 5
  |   ^
```

而 HUI 与 LARK 在第一行 `#` 处即终止，C2/C3/C4 暴露的问题完全无法呈现给学生。

> **最关键的教学安全发现**：HUI 对 C2（`=`）与 C3（`==`）**完全不报错**。因为 `=` 落在它的运算符字符类内，它会照单全收，产出一个「语义已错、却看起来能运行」的 token 流。对初学者而言，**错误被静默掩盖**比直接崩溃更有害——学生得不到任何反馈，却写出了行为错误的程序。

## 5. 四块关键代码残片分析

以下四块残片分别对应四种方案的核心机制，是上文实测现象的根因。

### 残片一：HUI —— master-regex 的「一刀切」与兜底崩溃

```python
# CIE-AL-CS-.../app/evaluator/tokenizer.py
token_specification = [
    ...
    ("OPERATOR", r"[+\-*/><=]"),   # ① '+'、'>'、'='、'<' 全部归为同一类
    ("NUMBER",   r"\d+(\.\d+)?"),
    ("STRING",   r'"[^"\n]*"'),
    ...
    ("MISMATCH", r"."),            # ② 兜底匹配任意单字符
]
...
elif kind == "MISMATCH":
    raise RuntimeError(f"Unexpected token: {value}")   # ③ 直接抛异常，无行列
```

- **①** 解释了 C2/C3 的**静默吞错**：`=`、`==` 都被 `OPERATOR` 吸收，词法层无从分辨「赋值/比较/Python 习惯」。
- **②③** 解释了 C1/C4/A1/A2 的**崩溃**：凡是字符类之外的符号（`#`、`!`、`：`、孤立 `"`）一律命中 `MISMATCH` 并抛出无位置、无引导的 `RuntimeError`。
- 两种失败模式并存——「太松」（吞错）与「太硬」（崩溃），恰恰都不利于教学反馈。

### 残片二：LARK —— RE 终结符 + 语法实现不全

```lark
// pseudocie/grammar.lark
statement: var_decl | const_decl | assignment | io_stmt | ";"   // ① 没有 IF / WHILE / FOR
...
INT_LITERAL:  /-?\d+/        // ② 负号写进数字（被 contextual lexer 化解）
CHAR_LITERAL: /'[^\\\n]'/    // ③ CHAR 只接受恰好一个字符
```

- **①** 解释了 C3/C4 的**报错位置错位**：grammar 未实现 `IF`，导致 `IF` 一旦出现，LALR 状态机立刻在 `IF` 后的 `Count` 处报 `Unexpected token IDENT`——错误指向了无辜的 `Count`，而非真正的混用点 `==`/`!=`，对学生是误导。
- **②** 是第二组测试的主角：理论歧义存在，但 contextual lexer 凭借分析器状态化解（这是工具方案的长处，须诚实承认）。
- **③** 解释了 B6/B7：刚性正则只接受单字符 CHAR，越界即报「无终结符匹配」，不解释语义约束。

### 残片三：BEAN —— 手写 + 领域引导（设计哲学的独立印证）

```python
# beancode/beancode/lexer.py
# 未闭合字符串：解释「真正原因」并给出建议
raise BCError(
    "could not find ending delimiter in literal\n"
    + "did you forget to insert an ending quotation mark?",
    self.pos(len),
)
...
# % 运算符：指出不支持，并给出替代写法
raise BCError(
    "% as an operator is not supported!\n"
    + "Please use the MOD(a, b) library routine instead of a % b!",
    self.pos(1),
)
...
# ENDFOR 误用：指出正确关键字
case "endfor":
    raise BCError(
        "ENDFOR is not a valid keyword!\n"
        + "Please use NEXT <your counter> to end a for loop instead.", p)
```

- BEAN 的作者**主动放弃正则、选择手写**，目的与本项目完全一致：为初学者提供「领域级」纠错引导（`%`→`MOD`、`ENDFOR`→`NEXT`、未闭合串的真实原因）。
- 这与 USER 的 `==`→`=`、`!=`→`<>`、`#`→`//`、中文标点纠正属于**同一种设计哲学**。两个相互独立的项目殊途同归，是对「面向初学者应当手写」这一取向的有力旁证。

### 残片四：USER —— detect → diagnose → heal 三步主动避障

```python
# compiler.py（tokenizer 主动避障，节选 != 分支）
if char == '!' and current_pos + 1 < source_length and source_code[current_pos + 1] == '=':
    errors.append(CompileError(ErrorSeverity.ERROR, current_line, start_column,
        "'!=' is not valid in pseudocode.",
        suggestion="Use '<>' for not-equals comparison.",   # ② 领域引导
        source_line=_src_line(current_line)))               # ③ 携带源码行
    tokens.append(Token(TokenType.NOT_EQUALS, "<>",         # ④ 自愈：补出正确 token
                        current_line, start_column))
    current_pos += 2
    continue
```

配套的结构化错误对象 `CompileError` 统一承载「分级 + 定位 + 引导 + 源码行 + `^` 指针」：

```python
class CompileError:
    def __init__(self, severity, line, column, message, suggestion=None, source_line=None):
        self.severity = severity; self.line = line; self.column = column
        self.message = message; self.suggestion = suggestion
        self.source_line = source_line

    def __str__(self):
        prefix = self.severity.value
        result = f"[{prefix}] L{self.line}:C{self.column} - {self.message}"
        if self.suggestion:
            result += f"\n  Hint: {self.suggestion}"
        if self.source_line is not None:
            stripped = self.source_line.rstrip('\n')
            result += f"\n  | {stripped}"
            if self.column > 0:                               # 列指针
                result += f"\n  | {' ' * (self.column - 1)}^"
        return result
```

- **①检测**：手动游标在任意位置都能前瞻判断（`!=`、`->`、`:=`、`==`、`#`、`;`、中文标点、en-dash、Unicode `←` 等一整套）。
- **②引导**：直接给出 Python/Pascal → CIE 的正确写法。
- **③定位**：行、列、源码行、`^` 指针四重定位。
- **④自愈**：补出等价的合法 token（`!=`→`<>`），让后续 parser 继续工作，从而支持「一次多报」。
- **错误分级**：`==` 记为 `Warning`（自愈后程序仍可生成），`!=`/`=`/`#` 记为 `Error`（阻止代码生成但不阻止继续诊断）。

## 6. 优缺点综合分析

### 6.1 分项优缺点

| 方案 | 优点 | 缺点 |
|------|------|------|
| **HUI**（纯正则） | 实现极简（约 60 行）；规则集中、易于增删 token | 错误处理只有「崩溃」或「吞错」两态；无行列定位；token 粒度粗；非 ASCII 字符直接异常 |
| **LARK**（工具生成） | 语法即文档；自动获得 LALR + contextual lexer；有行列定位；能化解部分词法歧义 | 错误信息「实现者视角」，无领域引导；语法不全会导致报错错位；无自愈；一错即停 |
| **BEAN**（手写） | 领域级纠错引导丰富；定位精确（行/列/span） | 代码量大；纠错规则需手工逐条维护 |
| **USER**（手写） | 定位+引导+分级+自愈+一次多报五位一体；最贴合教学目标 | 代码量与维护成本最高；纠错覆盖面依赖人工枚举 |

### 6.2 三个维度的横向排序

- **能力上限**：HUI（崩溃/吞错）< LARK（定位+化解歧义，但视角与完整性受限）< BEAN ≈ USER（detect→diagnose→heal）
- **错误信息质量**：HUI（无位置/误导/静默）< LARK（有位置、实现者视角）< USER ≈ BEAN（位置+领域引导+指针）
- **教学适配度**：HUI 最低（错误被掩盖最危险）< LARK 居中 < USER/BEAN 最高

### 6.3 关键洞察

1. **正则不是「一定差」**：LARK 的 contextual lexer 证明工具方案在「消歧」上甚至优于朴素 master-regex。
2. **但正则方案的错误信息有天花板**：它至多能告诉你「哪里不匹配」，做不到「识别你的意图 → 给出领域建议 → 自愈继续」。
3. **而这恰恰是教学场景最需要的**：初学者的错误大多不是「不懂语法」，而是「带入了其他语言的习惯」。这类错误需要的不是「报错即停」，而是「认出意图、指明正解、继续暴露更多问题」。
4. **静默吞错是教学的头号敌人**：HUI 对 `=`/`==` 的静默通过，比崩溃更有害——它让错误程序「看起来能跑」。手写方案通过显式检测从根本上规避了这一点。

---

## 7. 结论

对于「面向初学者的 CIE 9618 伪代码编译器」这一特定目标，**手写词法分析器是更优选择**。其价值不在于性能或实现简洁度（正则在这两点上反而占优），而在于它提供了**对错误处理的完全控制权**：能够实现精准定位、领域级引导、错误分级、自动纠正与一次多报。

实测数据与第三方项目 beancode 的独立选择共同支持这一结论：当设计目标是「教学友好」时，词法分析阶段的「detect → diagnose → heal」能力，是正则/工具生成方案难以企及、而手写方案天然擅长的核心竞争力。
