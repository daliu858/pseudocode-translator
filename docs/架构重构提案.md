# CIE 9618 伪代码编译器 — 架构重构提案 v2（终稿）

> 性质：**纯提案，零代码改动**。本版在 v1（综合 6 份外部资料调研）基础上，经 **gpt-5.5-extra-high** 与 **gemini-3.1-pro** 两次**独立**审核后定稿。两模型在无互相参考的情况下对三处问题给出几乎一致的批评，相关修正已全部纳入。
>
> 待办：交用户决定是否采纳。采纳后方进入实际编码（任务2），且仍遵循"agent 出补丁、人工审核、测试守门"。

## 0. 本版相对 v1 的关键修订（双审核共识）

| 项 | v1 | v2（修订后） | 修订理由（两模型一致） |
|----|----|----|----|
| 包 C（`_fields`+自动 generic_visit） | 纳入 | **否决** | CodeGen 是翻译器非遍历器，自动 generic_visit 删不掉任何方法、且会让未知节点静默生成半成品（应 fail-fast）。为根治一个 Parser 辅助函数 `_collect_stmt` 大改 AST 属杀鸡用牛刀。 |
| 包 E（统一 `_resolve`） | 查找顺序"①词法②继承" | **E-lite：严格"类字段优先于词法"**，照抄现状 | 现状 `visit_IdentifierNode` 是**类字段优先**；v1 写反了遮蔽顺序，会挂 OOP/BYREF 测试。 |
| 包 D1（DiagnosticCollector） | 引入可变 collector + 去重 | **入口一行 `set` 去重**（纯函数式），不引入新类 | 入口 `tokens, _ = tokenizer(src, all_errors)` 已丢弃返回值，P5 的"重复收集"bug **并不存在**；可变单例违背铁律1。 |
| 包 B（Span 贯穿） | "每个节点补 span，低风险" | **B-lite**：改 `_check_declared(name, node=None)` 签名取位置，先修 CodeGen 错误定位 | 不是纯加字段；要改签名并连带改 ~7 处调用，是中等改动。 |
| 包 D2（规则数据化） | JSON/dataclass 规则表 | **D2-lite**：抽 `_try_heal()` 函数，内部仍 if/elif | `#` 吃整行等"多字符前瞻消费"难用简单 pattern 表达；DFA 里塞正则变慢变难。表驱动是过度设计。 |
| 包 A | "极低风险" | 保留，**显式 import、不复用旧 `compiler_modules/`、`tokens.py` 不依赖 `errors.py`** | 旧模块是过时平行实现，误复用会制造两套 `TokenType`/AST 类身份导致 `isinstance` 失效。 |
| —（新增） | — | **新增"测试补强"前置**（做 D2 之前） | 两模型都指出：62 测试只覆盖编译、不验证运行时；且 `str(error)` 子串匹配是隐藏硬契约。 |

## 1. 三条铁律（不变）

1. **阶段间只用不可变数据结构通信**（CodeGen 不回调 Parser）。
2. **对外入口 `compile_pseudocode` 签名冻结 + `compiler.py` 薄 re-export** → 62 测试 import 与断言零改动。
3. **增量推进，每步 62 测试全绿才进下一步**；agent 只出补丁、人工审核。

> 补充隐藏契约（双审核强调）：**诊断文本稳定性**——`str(CompileError)` 的文本/severity/出现顺序是测试断言基础，任何改动需保持兼容（可先冻结 `__str__` 输出格式）。

## 2. 最终改动清单（6 项，按执行顺序）

### ① 包 A — 纯数据层拆分 + 薄入口（P1）
- 拆 `errors.py`、`tokens.py`、`ast_nodes.py`（只搬**当前 compiler.py** 的定义，**不碰旧 `compiler_modules/`**）。
- `compiler.py` **显式 re-export**：`TokenType / Token / ErrorSeverity / CompileError / 各 AST 节点 / tokenizer / Parser / PythonCodeGenerator / compile_pseudocode`（不用 `import *`，避免类身份分裂使 `isinstance` 失效）。
- 依赖方向（严格单向、无环）：`errors`；`tokens`（**不依赖 errors**）；`ast_nodes ← tokens`；`{tokenizer,parser,codegen} ← 上述`；`compiler ← 全部`。
- tokenizer/parser/codegen 三大逻辑块**暂不拆**（可作未来可选）。
- 风险：低。验收：62/62 全绿。

### ② 包 B-lite — 修 CodeGen 错误定位（P4）
- 把 `_check_declared(self, var_name)` 改为 `_check_declared(self, var_name, node=None)`，从 `node`（或其 `.token`）取行列，替换写死的 `(0,0)`；同步更新 ~7 处调用点。
- **不**做"全 40+ 节点补 span"（收窄范围）。
- 风险：低-中。验收：未声明变量报错带正确行列；62 测试通过；可新增 1-2 个定位测试（不改现有 62）。

### ③ 包 E-lite — 抽统一查找 helper（P3，**严格保持现状优先级**）
- 抽 `_resolve(name)` / `_is_class_field(name)` / `_lookup_lexical(name)` / `_format_identifier(node)`，收拢 `_check_declared` 与 `self.` 前缀判定的重复逻辑。
- **查找顺序必须照抄现状：类字段（`_class_fields`，含继承链）优先 → 再词法 `scope_stack` 内→外 → 全局/内建**。绝不反转遮蔽顺序。
- 不引入独立 Resolver pass（留作未来可选）。
- 风险：低（行为等价）。验收：OOP 继承 + BYREF + 同名参数相关用例全过。

### ④ 包 D1' — 入口纯函数去重（P5）
- 删除"引入 DiagnosticCollector"的想法。仅在 `compile_pseudocode` 返回前，对 `all_errors` 按 `(severity, line, col, message)` 做一次 `set` 去重（保持原顺序）。
- 风险：极低。验收：62 测试通过（若某测试依赖重复错误条数，先确认无）。

### ⑤ 测试补强（前置于 D2，**新增独立文件、不改现有两文件**）
- 新增 `test_diagnostics_snapshot.py`：对若干输入快照 token 序列 + 错误文本 + severity + source_line，作为 D2 的安全网。
- 新增 `test_runtime.py`：对无 INPUT 的样例 `exec` 生成的 Python 并比对输出，补 P6（运行时）盲区，重点覆盖 BYREF / OOP 继承。
- **约束**：不修改 `testclass.py` / `test_runner.py`（用户禁区）；新增文件需用户同意。
- 风险：低（纯新增）。

### ⑥ 包 D2-lite — 抽 `_try_heal()` 函数（P2）
- 把 tokenizer 主循环里 ~10 条非常规字符/组合的 detect→diagnose→heal 规则，挪进一个**纯函数 `_try_heal(...)`**，内部仍用 if/elif，主循环只在"遇到异常分支"时调用它。
- **不上**数据驱动表/JSON schema（过度设计）。
- 放最后做（动 tokenizer 热路径），由步骤⑤的快照测试守护。
- 风险：中。验收：诊断快照一致 + 62 测试通过。

## 3. 推荐执行顺序

```
A（数据层拆分+薄入口）
  → B-lite（CodeGen 错误定位）
  → E-lite（统一查找 helper，类字段优先不变）
  → D1'（入口一行 set 去重）
  → 测试补强（诊断快照 + 运行时小测，新增不改 62）
  → D2-lite（抽 _try_heal 函数）
```
每步 62 测试守门；任意步可独立回滚。

## 4. 已否决 / 降级（连同理由存档）

| 条目 | 处置 | 理由 |
|------|------|------|
| 包 C：自动 `generic_visit` 进 CodeGen | **否决** | 翻译器需 fail-fast，自动遍历会静默产出半成品，且删不掉方法 |
| `_fields` 元数据 | **暂缓**（未来若做 dump/lint/transformer 再加，且只用于独立 `AstWalker`，不动 CodeGen） | 当前无实际用途（YAGNI） |
| DiagnosticCollector 可变单例 | **否决** | 违背铁律1；P5 bug 实际不存在 |
| 规则表 JSON/schema（id/applicability/enabled…） | **否决** | 小项目过度设计 |
| 独立 Resolver pass | **未来可选** | 中成本，当前 helper 即可 |
| 物理拆分 tokenizer/parser/codegen 到多文件 | **未来可选** | 数据层独立后再按需 |

## 6. 关于用户最初的 pub-sub（ROS2）设想

用户最初受 ROS2 的 publisher–topic–message 解耦启发。**双审核与调研的结论是：对一个 2300 行、单次毫秒级编译的源到源编译器，引入 pub-sub 中间件属过度工程。** 但 pub-sub 的**精神内核——"组件间通过稳定的数据契约解耦，而非直接互调"——已被采纳**，落地为更轻、更契合的形式：**铁律1（阶段间不可变数据通信）+ 包 A（数据层独立）+ 各阶段明确 I/O 契约**。这达到了同样的"下层可替换、易 debug"目标，却不背负消息总线的复杂度。
